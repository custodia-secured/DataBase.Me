# M4: Search and query

**Status:** built and checked on `m4-search`, not yet in a pull request. **Started:** 2026-11-02, on
branch `m4-search` from `main` at `176abfd` (M3 merged). On 2026-11-01 the maintainer asked for
forward progress over waiting, so the plan below was written and built in one stretch, and its
decisions are listed for review at the end rather than before.

## Plan

**Scope (handoff brief §8):** FTS5 full-text search, facets, the query DSL, saved views and a
command palette.

**Acceptance:** search under 50 ms on 100,000 objects, as a CI benchmark; golden tests for the DSL.
Carried from M2 and M3: keyboard-operable, a screen-reader alternative, 360 px with touch, the app's
CSP.

**Design (ADR-0020).**

- **The index.** Migration 2 adds `search_text` (one row per live object: `title`, `body`,
  `props_text`), `fts` (an FTS5 external-content index over it, `unicode61 remove_diacritics 2`,
  kept in step by triggers) and `search_dirty`. All three are derived and can be rebuilt. A
  transaction notes the objects whose text it may have changed, one short insert each, and the next
  search brings those rows up to date first: so undo, redo and trash are covered without the op log
  knowing about search, a bulk change pays nothing for the index until someone searches, and a
  search never sees stale text. The body is the summary and the plain text of the blocks in tree
  order, with mentions left out; `props_text` is the string and number values of the fields.
- **Ranking.** BM25 with the title weighted 10, field values 2 and the body 1. The text a person
  types never reaches FTS5's query syntax: it is split into words, each quoted, with a prefix match
  on the last while it is being typed. Quoted phrases stay phrases.
- **The DSL.** A JSON `Query` in `dbme-core`: `from` (types, with their subtypes, and `under`),
  `where` (conditions on built-in columns, written `$title`, `$created_at` and so on, or on field
  keys), `search`, `related_to` (one hop, either direction, optionally one relation type), `sort`
  (now with `relevance`), `limit` and `offset`. The store compiles it to one prepared statement with
  bound parameters; nothing from a query is spliced into SQL. Twelve golden tests hold the SQL and
  the parameters each query compiles to.
- **Facets.** The counts of a query's results per type, or per value of one field, with
  multi-select values counted one by one.
- **Saved views.** A `views` table written through the op log like every other table, so Undo
  covers saving, renaming and deleting a view. The sidebar lists them, and opening one runs its
  query.
- **The command palette.** Ctrl+K (⌘K) anywhere, and a Search button in the header. Typing searches
  the whole vault and shows titles with a snippet; a line starting with `>` lists commands instead:
  switch view, new page, undo, redo, split, open a saved view. An ARIA combobox with a listbox.
  Ctrl+Enter shows every result on the results surface, where facet chips narrow the query and a
  search is saved as a view.
- **Commands.** `search`, `objects_query`, `objects_query_count`, `facets`, `views_list`,
  `view_get`, `view_save`, `view_update`, `view_delete`: 36 becomes 45.

## Decisions to confirm

1. The index is kept by the store, not by SQL triggers on `objects` and `blocks`, because the body
   is text drawn from block JSON by rules that live in Rust.
2. Changes queue and reads flush: the index is brought up to date by the next search, not at
   commit. With the index written at commit, the M1 budget took 1.99 s of its 2 s in a release
   build here; with the queue, 1.28 s. The cost moves to the first search after a large change:
   1.3 s after 100,000 objects, about a row's worth after one edit.
3. `search_text` as a content table beside `fts`, rather than `fts` holding the text, so a row can
   be replaced by its `object_id` without scanning the index.
4. The DSL's field naming: `$column` for built-in columns, a bare key for a field.
5. `related_to` is one hop in M4; depth waits for the graph view (M8).
6. Saved views go through the op log.
7. The brief's "also typed as text" form of the DSL is the palette's own small syntax (plain words,
   quotes for phrases, `>` for commands), not a second grammar; a text grammar waits for NL → DSL
   (M11).
8. Only select and multi-select fields become facet chips; the rest waits for the filter editor
   (M8), as do saved views in the Table and Gallery.
9. The `search` command stands beside `object_search`, the title lookup "Move to…" and "Relate to…"
   still use, which wants titles that start with what was typed.

**Tests, locally.** `cargo test --workspace`: passes, with new store tests for search (8), the DSL
(7), the goldens (1) and views (3), and 7 new unit tests in core and store. `search.spec.ts`:
20 passed on the four functional projects, 0 failed. The whole e2e suite with its budgets: 201
passed, 0 failed, 25 skipped; the map opens in 286 ms and an edit shows in 33.9 ms, as before. Lint,
format, types and the unit tests pass. The launch check now searches over real IPC too.

**Found while measuring.** The first run of the benchmark put a search with a type filter and a
field condition at 29 s: the planner ran the full-text match once per object. Fixing the join order
with `CROSS JOIN` brought it to 58 ms, and replacing the `IN` over every object of the types with an
`EXISTS` per candidate to 4.6 ms. The first run also showed the M1 budget at 1.99 s of 2 s with the
index written at commit, which is why changes now queue and reads flush (Decision 2).

## Results

Release build, development machine, 100,000 objects, half with a paragraph, best of three (the
first run in brackets); budget 50 ms:

| Search                                          | Best (first)      |
| ----------------------------------------------- | ----------------- |
| One common word                                 | 5.4 ms (8.4 ms)   |
| Two words                                       | 2.1 ms (2.4 ms)   |
| A prefix                                        | 5.0 ms (5.3 ms)   |
| A phrase                                        | 1.0 ms (1.2 ms)   |
| A rare word                                     | 0.05 ms (0.1 ms)  |
| A field value                                   | 12.9 ms (13.5 ms) |
| Search with a type filter and a field condition | 4.6 ms (12.2 ms)  |
| Its count (1,147 results)                       | 2.1 ms (2.6 ms)   |
| Its facets by status                            | 2.8 ms (2.9 ms)   |
| One page of everything, not gated               | 16.2 ms (20.1 ms) |
| The type facet of everything, not gated         | 21.5 ms (27.3 ms) |

Seeding took 4.5 s. The first search after it brought the index up to date with all 100,000
objects in 1.3 s. The M1 budget runs at 1.28 s (create 243 ms, edit 143 ms, delete 316 ms, undo
582 ms), and the M3 tree read at 11.7 ms.

## Not verified

- **CI.** Nothing in this milestone has run on a shared runner yet.
- **The real app.** The palette, the results surface and saved views have been driven only on the
  e2e server. The launch check covers none of the nine new commands.
- **Scale in the app.** The benchmark is the store's; no e2e budget drives the palette on a large
  vault.
