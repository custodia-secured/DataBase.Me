**Status:** closed 2026-10-25. CI run 40237915788 of pull request #3 (`m1-vault-core` at
`ecb8afc`) passed every job, including the performance budget at 1.68 s. The first run, at
`710e87b`, failed the budget at 2.60 s; the fix is Deviation 9. Merging waits on the maintainer's

## Plan

**Scope (handoff brief §8):** schema and migrations, object/type/field/relation services, op log
with undo and redo, blob store with deduplication, typed IPC (commands and an event stream).

**Acceptance:** at least 90% line coverage on `crates/core` and `crates/store`; creating, editing,
deleting and undoing 10,000 objects takes under 2 s; killing the process during a write leaves a
valid vault; the core crates cross-compile for `aarch64-apple-ios` and `aarch64-linux-android` in
CI.

**Tasks.**

1. `dbme-core` (pure domain, no I/O, no SQL): ULIDs with a monotonic generator and an injectable
   clock; fractional sort keys; `blake3:` hash strings; the entity models and field kinds with value
   validation; op kinds and payloads, their inverses, and the exact bytes each op hash covers; the
   seeded system types.
2. `dbme-store` (all SQL, as prepared statements): numbered migrations with `application_id`,
   `user_version` and a refusal to write newer vaults; WAL and foreign keys; one generic engine that
   applies an op only if the rows still match the op's "before" state, and appends it to the
   hash-chained log in the same transaction; transactions (one undo step each) with services for
   types, fields, objects (create, update, move, trash, restore), object types, blocks, relations
   and attachments; undo and redo; the BLAKE3 blob store (temporary file and rename, deduplicated);
   `verify` (hash chain, SQLite integrity and foreign keys, blob presence, and replaying the log into
   a fresh database to check it reproduces the tables).
3. Desktop: Tauri commands and a `vault://changed` event, with TypeScript bindings generated from
   Rust and checked in; CI fails if they are stale. The launch test also creates a vault, creates an
   object and undoes it over IPC.
4. CLI: `dbme vault create`, `dbme verify`.
5. Tests: unit tests; property tests (random edit sequences keep the chain valid, replay reproduces
   the state, undo-all then redo-all round-trips); a crash test that kills a writer process at random
   moments and then verifies the vault; deduplication; a release-mode budget test for the 10k
   create/edit/delete/undo run; a criterion benchmark.
6. CI: coverage gate (cargo-llvm-cov, at least 90% of lines in `dbme-core` and `dbme-store`); iOS
   and Android cross-compile jobs; the budget test.
7. Docs: FORMAT.md §2 (sort keys), §3 (tables) and §5 (op log) move to Decided; CHANGELOG.

**ADRs.**

- 0012 Op log: payloads, hashed bytes, groups, undo and redo.
- 0013 Sort keys: the fractional-index algorithm.
- 0014 Typed IPC: how bindings are generated, and the event stream.
- 0015 SQLite settings and migration policy.

**Risks.**

- The 2 s budget: every op is hashed and logged. Measured early; bulk actions run as one
  transaction.
- Cross-compiling bundled SQLite and BLAKE3's C code needs the Android NDK and Xcode in CI.
- `tauri-specta` is a release candidate (2.0.0-rc.26), so it is pinned exactly; ts-rs is the
  fallback (ADR-0014).
- 90% coverage includes error paths, so failure cases need their own tests.
- Killing processes on Windows can leave files locked; the crash test retries opening.

**Planned deviations from the brief (each in an ADR).**

- `ops` gains `group_id` (the undo step an op belongs to) and `undo_of` (the step it reverses).
  A `vault_meta` table holds the vault's ID and format version.
- Tables used only by later milestones (`views`, `canvas_items`, `spaces`, `ai_audit`,
  `mirror_state`, `conflicts`, `provenance`, `fts`, `vec_chunks`) arrive with those milestones'
  migrations, not in M1.
- Undo is per session (in memory). It refuses, and changes nothing, when someone has edited the
  same data since: it never overwrites a later edit.

## What was built

- **`dbme-core`:** ULIDs with a monotonic generator and an injectable clock; fractional sort keys
  (ADR-0013); `blake3:` hashes; the data model with field-value validation (FORMAT.md §3.3); ops
  with preconditions, inverses and diffing; the op hash chain (ADR-0012); the 25 system types.
- **`dbme-store`:** the vault folder (atomic creation, one-writer lock, `FORMAT.md` copy), SQLite
  settings and migration 1 (ADR-0015), services for types, fields, objects, blocks, relations and
  attachments, undo and redo, sort-key rebalancing, the deduplicating BLAKE3 blob store, and
  `verify` with full replay.
- **CLI:** `dbme vault create <path>`, `dbme verify <path> [--deep] [--json]`.
- **Desktop:** 15 typed commands and the `vault-changed` event, with generated TypeScript bindings
  (ADR-0014); the launch test drives a real vault over IPC.
- **CI:** `coverage` (both crates, 90% each), `mobile` (iOS and Android), `budget` (gate, then the
  per-transaction measurement).
- **Docs:** FORMAT.md draft 1 (§1, §2.1, §3, §3.3 and §5 decided); ADR-0012 to ADR-0015;
  CHANGELOG.

## Deviations and decisions to confirm

1. **How the 2 s budget is read (ADR-0015).** It is met for bulk actions, one transaction each,
   which is how the app applies imports, pastes and multi-selections. With every change in its own
   transaction, the same 40,000 changes take 4.59 s, almost all of it SQLite committing to disk.
2. **Event name `vault-changed`, not `vault://changed`** (ADR-0014): tauri-specta names events in
   kebab case.
3. **Integers cross IPC as JavaScript numbers** (ADR-0014): every `i64` sent is a timestamp or a
   log position, far below 2^53.
4. **Schema additions** as planned: `ops.group_id`, `ops.undo_of` and the `vault_meta` table
   (ADR-0012). Later milestones' tables are not created yet (FORMAT.md §3.4).
5. **A second ignored advisory:** `paste` (RUSTSEC-2024-0436) is unmaintained, not vulnerable.
   It is a build-time macro used by specta. Recorded in `deny.toml` under the ADR-0009 rule.
6. **A 32 MiB SQLite page cache** per open vault (ADR-0015): about 5% faster bulk transactions,
   within the 300 MB idle-memory budget.
7. **Windows test manifest** (ADR-0014): `build.rs` embeds the Common Controls v6 manifest into
   every Windows binary, so the desktop crate's test binary can start. Without it the test exits
   with `STATUS_ENTRYPOINT_NOT_FOUND`.
8. **ADR numbering:** ADR-0011 (funding through Stripe) is on the unmerged `m0-followups` branch.
   Merging both branches gives a one-line conflict in `docs/adr/README.md`.
9. **Query shapes chosen for the budget (ADR-0015).** Updates set only the columns that changed;
   object and block subtrees, and an object's block tree, are walked in Rust instead of recursive
   SQL; short per-object lists are sorted in Rust; an attachment's blob size comes from a subquery
   instead of a join; undo applies each inverse to the row it has just read. The results and their
   order are unchanged: a new test compares each read with its SQL definition, and fails when the
   ordering is deliberately broken.

## Known issues

- **The budget's margin on CI is 16%:** 1.68 s against 2 s, in the one run so far. Undo, at
  859 ms, is the largest phase. A slow runner could fail the job without a code change. The 4-core
  reference machine (ADR-0008) is untested. What remains is about 13 µs per op, spread across
  building, hashing and logging the op and its SQL (ADR-0015).
- **Coverage gaps:** `seed.rs` is at 65.6%. Its uncovered lines are two `const fn` constructors,
  which run at compile time where coverage cannot see them, and an error path the fixed type list
  never reaches. `sql.rs` and `identity.rs` are at about 85%; their missed lines are not yet
  reviewed one by one.
- The `paste` advisory stays ignored until specta leaves release candidates.
- WebView2 still prints `Failed to unregister class Chrome_WidgetWin_0` on smoke-mode exit
  (harmless, as in M0).

## Proposed plan for M2 (editor and basic views)

- **Scope (brief §8):** block editor, Document, Outline, Table (virtualised), Gallery, the
  hierarchy sidebar, backlinks. **Acceptance:** live consistency across views; a 100k-row table at
  60 fps; everything keyboard-operable; every view passes e2e tests at 360 px width with touch.
- **Tasks:** IPC commands for blocks, relations and queries over the M1 services; a UI vault store
  that listens to `vault-changed` and refetches only what changed; the block editor (an ADR choosing
  the editor library, under the M0 licence and CSP rules); Document and Outline views with
  rebalancing on long keys; a virtualised Table with inline field editing; a Gallery; the hierarchy
  sidebar with drag-and-drop moves; backlinks from `relations`; Playwright e2e tests at desktop and
  360 px with touch emulation; the 100k-row scroll benchmark.
- **ADRs:** editor library; UI state and cache strategy; e2e test harness for the Tauri webview.
- **Risks:** editor libraries vary in licence and in mobile and IME support; 60 fps at 100k rows
  needs virtualisation and paginated IPC; e2e tests against a real Tauri webview differ by OS.
