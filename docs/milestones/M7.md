### What exists already

- Dark colours follow the OS (`packages/ui/src/tokens.css`, `prefers-color-scheme`), and the
  tokens file says a theme chosen in Settings will set `data-theme` on `<html>` and win.
- The shell opens one default vault in the app's data folder (ADR-0017); there is no picker and
  no settings surface. The files folder's location override lives in the app's config folder
  beside the identity (M5).
- The app writes `FORMAT.md` into every vault it makes (`dbme-store`, `FORMAT_FILE`).
- The smoke launch prints `startup_ms`; CI builds the release binary on three systems with
  `tauri build --no-bundle` and launches it. No installer, no release workflow, no signing.
- The bug-report template already asks for the diagnostic report and says it ships with 0.1.
- No updater plugin (ADR-0010); the window's drop, the dialogs and the palette are the UI's
  surfaces; views are a registry of five.

### Design (ADR-0027 settings, modes and themes; ADR-0028 onboarding and the network guarantee; ADR-0029 the release)

- **Settings are the person's, not the vault's.** One `settings.json` in the app's config folder
  (beside the identity and the files-folder override), read and written by `dbme-api`
  (`Settings` struct, versioned with a `version` field and defaults for every missing key, so an
  older file always loads). Keys in 0.1: `mode` (`simple` | `organizer`), `theme` (`system` |
  `light` | `dark`), `update_checks` (bool, default false), `last_vault` (path), `onboarded`
  (bool). Commands `settings_get` and `settings_set(patch)`; a `settings-changed` event so two
  windows (later) agree. A vault stays portable: nothing about a person's screen or habits goes
  into it. The vault's `themes/` folder of FORMAT.md waits for the theme editor (v1); 0.1 ships
  light and dark only, and FORMAT.md says so.
- **Themes.** `theme` sets `data-theme` on `<html>` at startup and on change; `system` removes it
  so the OS media query decides. Both palettes pass WCAG 2.2 AA contrast for text, controls and
  focus rings (axe checks colour contrast in the e2e runs, which gain a dark pass on the
  Document and Table views). No flash of the wrong theme: the shell reads the setting before the
  UI mounts.
- **Modes are presets of what is shown**, changeable any time, the same on every platform (brief
  §2.9). _Simple_ shows the Document, Outline, Mind map and Gallery views, the pages tree, search,
  the files folder, import, and a daily journal ("Today" in the palette and the sidebar: opens or
  makes a Note titled `YYYY-MM-DD` under a top-level "Journal" page); it hides types and fields
  (the types line, the properties, the Table view, the type picker in the source picker), so
  everything reads as a Note or a File. _Organizer_ shows all of it. The mode is a filter in the
  UI, never a change to the vault: a vault made in Organizer opens unchanged in Simple. Researcher
  and Data/Power modes are later milestones and are listed greyed with their milestone.
- **Onboarding** runs when `onboarded` is false and no vault is open: welcome; where the vault
  goes (the default folder, or a folder the person picks with the native dialog, if gate 1a admits
  `tauri-plugin-dialog`; else a typed path, as the files-folder override is); the files folder (on
  by default in its default place, or off, or a folder); the mode (Simple highlighted); the theme;
  update checks (off, highlighted; the text says plainly that turning them on would send the app's
  version and the person's address to the download host, and that 0.1 has no updater yet, so the
  choice is recorded for the first version that does). The AI question is M11 (brief §2.5, build
  plan Decision 7). "Set up again" in Settings reopens it. Nothing in onboarding touches the
  network.
- **Settings and Help** are one dialog from the header and the palette: the vault (its path, open
  another, make a new one), the files folder (the M5 dialog, linked), the mode, the theme, update
  checks, and Help: the version, the format version, where the docs and the issue tracker are (as
  text to copy; the app opens no browser in 0.1, so no opener plugin and no request), and _Copy
  diagnostic report_.
- **The diagnostic report** is plain text the person pastes into an issue: app version, format and
  schema versions, OS and architecture, webview and its version, the mode and theme, whether the
  files folder is on, and the last twenty error codes the shell saw (the command name, the
  `IpcErrorKind`, the time) with no messages, since a message can carry a path or a title. Counts
  of objects and blobs are included (numbers, not content). Copied with the clipboard API of the
  webview (a secure context under Tauri's protocol), so no plugin.
- **Zero network requests on first launch with defaults.** Gated on Linux in CI: the release app
  is launched through its smoke test under `strace -f -e trace=connect,sendto,sendmsg` on the
  virtual display, with a fresh config folder so onboarding's defaults apply, and the test fails
  on any socket call to an address that is not loopback or a Unix socket. WebKitGTK's own
  behaviour is what the probe records (gate 1b). Windows (WebView2) and macOS (WKWebView) cannot
  be traced that way on a shared runner; they are checked by hand once per release with the OS's
  own tools (the procedure in `docs/user-guide/privacy.md`) and the result written into the
  release notes, as ADR-0010 asked. The e2e harness also fails any page request that leaves the
  e2e server's origin, which catches a stray `fetch` in the UI on every run.
- **The usability scenario** is one e2e spec at both sizes, `scenario.spec.ts`, in the brief's
  five steps: capture (a new note typed in Simple mode, "Today"), organize (switch to Organizer,
  give it a type and a field, move it under a page), find (the palette by a word in its text),
  edit a file outside the app (the files folder on, the file changed on disk, the change in the
  app), export (the JSON and CSV export and the full export written). The same steps are written
  for a person in `docs/user-guide/first-ten-minutes.md`, which is the scripted scenario of the
  acceptance when someone runs it by hand.
- **Docs and the docs site.** `docs/user-guide/` in Markdown: getting started (install, the first
  launch), the vault and where it lives, pages and views, the files folder and Obsidian,
  importing, settings, modes and themes, keyboard and accessibility, privacy (the no-network
  promise and how to check it), reporting a problem (the diagnostic report), and the first ten
  minutes. Published by GitHub Pages from `docs/` with its built-in renderer, so no generator is
  added to the repository; a `_config.yml` names the title and excludes nothing (Decision 5). The
  README gains install, screenshots and the donate link the brief asks for. FORMAT.md goes to
  **v0.1**: every section whose ADR is accepted is marked Decided, the rest stay Draft with their
  milestone, the table of drafts gets its v0.1 row, and the copy the app writes into vaults is
  this one.
- **Installers and the release.** `release.yml` runs on a `v*` tag: the three desktop runners
  build with `tauri build` (MSI and NSIS on Windows; DMG on macOS for Apple Silicon and Intel;
  AppImage and deb on Ubuntu 22.04), compute SHA-256 sums, and attach everything to a draft
  GitHub Release with the CHANGELOG's section as its notes. Signing runs when the secrets exist
  and is skipped with a notice when they do not: Authenticode for Windows, Developer ID and
  notarization for macOS; Linux artifacts are not signed in 0.1. Whether the secrets exist is the
  owner's decision and cost (Decision 6); 0.1 can ship unsigned, with the docs saying what the OS
  will warn and how to verify the checksums. The app identifier `org.databaseme.desktop` becomes
  final with the tag unless the owner changes it before (ADR-0001; Decision 7). The version
  becomes 0.1.0 in the workspace `Cargo.toml` and `apps/desktop/package.json` (one place each,
  checked equal by a test since M0).
- **Budgets.** The brief's cold start (< 2 s to usable at 100k objects) is measured once at
  close-out from the smoke launch's `startup_ms` on a 100k-object vault made by the CLI, here and
  on the three CI systems, and recorded; it gates nothing in M7 (the budgets job gates what M1
  gated). The idle-memory figure (< 300 MB) is read the same way and recorded.

## Decisions to confirm

1. Settings live in `settings.json` in the app's config folder, not in the vault; the vault stays
   portable and carries nothing about a person's screen.
2. Simple mode hides types, fields and the Table view and adds "Today"; Organizer shows
   everything of M1 to M6. The mode never changes the vault.
3. "Update checks" is a recorded choice in 0.1: there is no updater (ADR-0010), so neither answer
   causes a request; the first version with an updater honours it.
4. The zero-network gate runs on Linux with `strace`; Windows and macOS are checked by hand per
   release with the OS's tools and recorded in the release notes.
5. The docs site is GitHub Pages rendering `docs/` as it is, with no generator dependency. **Needs
   the owner:** the Pages setting on the repository, and the URL to print in Help.
6. Installers are built unsigned unless the signing secrets exist. **Needs the owner:** whether to
   buy an Authenticode certificate and an Apple Developer ID for 0.1, or ship 0.1 unsigned and
   say so.
7. The identifier `org.databaseme.desktop` becomes final with the 0.1 tag. **Needs the owner:**
   the trademark and domain check owed since M0 (build plan §8, "still open").
8. The daily journal is a dated Note under a "Journal" page, made on first use.
9. The AI question waits for M11, as the brief orders it.
10. The native folder picker comes in only if gate 1a admits its plugin; otherwise typed paths
    stay, as in M5 and M6.

Still open from M6: Decisions 1 to 17 and ADR-0026; from M5: the 27 decisions and five ADRs; the

## Gate results (2026-11-03)

- **1a, the dialog plugin.** `tauri-plugin-dialog` 2.8.4 (MIT OR Apache-2.0) added to the shell:
  `cargo deny check licenses bans sources` clean with no new exception; it brings
  `tauri-plugin-fs` 2.7.1, `rfd` 0.17.2 and `raw-window-handle` 0.6.2, and on Windows nothing
  beyond `windows-sys`. It is a dependency only until Task 5 registers it; a plugin that is not
  registered runs nothing at launch. Admitted (Decision 10): the picker is native.
- **1b, the network probe.** `scripts/network-probe.mjs` reads an strace log of the smoke launch
  (`DBME_SMOKE_WRAP` in `smoke-launch.mjs`) and fails on any internet socket call to an address
  outside the machine; the Linux desktop job runs it, advisory (`continue-on-error`) until Task 8,
  and keeps the trace as the `network-trace` artifact. **Result** (CI run 41629225759 on
  `c04f22d`, Linux desktop job): `0 internet socket call(s) in the trace, 0 outside the machine`,
  `✓ no network request on first launch with default settings`. The gate holds; Task 8 makes it
  blocking.
- **1c, the clipboard.** The smoke launch's checks now write a line to the webview's clipboard
  and read it back, and the shell prints the outcome as a `DBME_SMOKE_NOTE`. **Result** (the same
  run): both desktop jobs that reached the smoke launch printed `note: clipboard: write failed
(The request is not allowed by the user agent or the platform in the current context, possibly
because the user denied permission.)`. The page's clipboard is not given to the app's webview
  under the smoke launch's conditions, so the diagnostic report (Task 7) cannot rely on it: the
  dialog shows the text to copy by hand whenever the write fails, and the e2e test accepts
  either outcome. **Found at Task 11:** on Windows the probe's read back (`readText`) never
  answered: WebView2 raises a permission question for a clipboard read, nobody is there to
  answer it in a smoke launch, and the Windows desktop job waited the full 120 s and failed
  ("no ready signal", run 41632622083, and the same on this machine). The probe now writes only,
  which is all the report needs, and gives the write two seconds; nothing in the app reads the
  clipboard. Windows' write outcome is in the Task 11 entry.
- **1d, Pages.** Not checkable until the owner turns Pages on for the repository (Decision 5);
  GitHub's Pages renderer takes `docs/` as it is, and the HTML comment at the top of FORMAT.md is
  legal Markdown. Checked when enabled.
- **1e, the bundles.** `release.yml`'s first run on the branch (41627078495, unsigned, version
  still 0.0.0): Windows `DataBase.Me_0.0.0_x64-setup.exe` 5.8 MB (NSIS) and
  `DataBase.Me_0.0.0_x64_en-US.msi` 8.4 MB; Linux `DataBase.Me_0.0.0_amd64.deb` 9.2 MB,
  `DataBase.Me-0.0.0-1.x86_64.rpm` 9.2 MB and `DataBase.Me_0.0.0_amd64.AppImage` 86.9 MB (the
  AppImage carries its runtime). **Found:** both macOS targets failed in `codesign`, because an
  empty `APPLE_SIGNING_IDENTITY` from a missing secret counts as set; the signing variables are
  now exported only when the secrets exist, and the macOS figures come from the second run
  (41629117934): `DataBase.Me_0.0.0_aarch64.dmg` in `installers-macos-arm64` (8.35 MB) and
  `DataBase.Me_0.0.0_x64.dmg` in `installers-macos-x64` (8.66 MB), unsigned. Every target builds; the sizes are within Decision 8's
  expectations (the AppImage's 87 MB is the runtime it carries, and is noted in the user guide).
