## Plan

**Scope (brief §8, build plan row M6):** importers for a Markdown or Obsidian folder, CSV and
XLSX (rows become objects), PDF text, and images with EXIF and thumbnails; drag-and-drop of any
file; import runs with a dry-run preview, a dedupe report and undo; provenance on every imported
object. The `crates/ingest` crate the brief's §7 names, and the `provenance` table of §4 and
FORMAT.md §3.4. Sidecars (Docling, whisper.cpp, ffmpeg, OCR) are M12 and nothing here may depend on
one; email, archives, takeouts and the clipper are M9 and M12.

### Design (ADR-0026, to be written in Task 10)

- **One crate, portable by construction.** `crates/ingest` (`dbme-ingest`) depends on `dbme-core`,
  `dbme-store` and `dbme-mirror` (for the Markdown importer, below) and on pure-Rust parsers only,
  no C and no platform code, so the importers can run on mobile (M14); the sidecar manager the
  brief puts in this crate is M12 and desktop-only, behind a trait then. The crate is not added to
  the mobile CI job (which builds `dbme-core` and `dbme-store`) until M14 needs it; that it stays
  portable is a `cargo deny` sources check and a review item, not a gate. `dbme-mirror` depends
  on `notify`, which is desktop-only: the dependency is therefore **optional**, a feature
  `markdown` on by default, so a mobile build can take the crate without the watcher.
- **The contract (build plan 359).** `Importer { id(), accepts(&Sniffed) -> bool,
plan(&Source, &Ctx) -> Result<Extract> }` where `Sniffed` is the file name, extension, size and
  the first bytes' MIME (`infer`), `Source` is a file or a folder, and `Extract` is the plan's
  product: objects (title, type, props, blocks, attachments by role), relations, derived blobs
  (thumbnails, extracted text), warnings, and one `ProvenanceDraft` per object (`source_kind`
  `import:<importer id>`, `source_uri` the absolute path or `path#sheet` or `path#page`,
  `original_blob`, `extractor` and `extractor_version` from the crate, `confidence`). The
  pipeline is the brief's: sniff → hash and dedupe → store the blob → extract → map to type →
  (enrich: none in M6) → index (search's own dirty table does it) → provenance.
- **A run is a plan, then an apply.** `ingest::plan(sources, options) -> ImportPlan` reads every
  source, runs the importer that accepts it (the generic one otherwise) and writes nothing to the
  vault; it stores no blob either, hashing in memory, so a dry run leaves no trace. The plan
  carries, per source: the importer, the type and field changes it would make, the objects with
  their titles, the duplicates found, the warnings, and samples for the preview. `ingest::apply(
vault, plan) -> ImportRun` then writes **one transaction**: new types and fields, blobs
  (`BlobStore::put`), objects, blocks, relations, attachments, provenance rows. One transaction is
  one undo step, which is the "undo" the brief asks for; a run too large for one transaction (the
  informational budget below) is split into transactions of 10,000 objects, each an undo step, and
  the plan says so. The `import_run_id` of every provenance row is the run's ULID; there is no
  `import_runs` table (Decision 2): the run is recoverable from `provenance` by its id and from
  the op log by its group ids.
- **Provenance is op-logged** (Decision 1): a new entity `provenance` with `create` and `delete`
  ops, so a run's provenance rows undo with the run, replay in `verify`, travel in `ops.jsonl`
  and so survive the full export round trip (FORMAT.md §7), and will sync. Migration 4 creates
  the table with the brief's columns (`id`, `object_id`, `source_kind`, `source_uri`,
  `import_run_id`, `original_blob`, `extractor`, `extractor_version`, `confidence`, `accepted`,
  `created_at`), with an index on `object_id` and one on `import_run_id`; `verify::TABLES` gains
  it. The files folder's provenance stays the derived device (M5 Decision 1): the folder's inbound
  path writes no provenance row in M6, and `source_kind = file:external` is reserved for a later
  milestone that wants it there too (ADR-0021 note).
- **Dedupe (Decision 3).** By content hash, which the blob store already keys on: a source whose
  hash is attached as `Original` to a live object is a duplicate, listed in the report with that
  object, and skipped unless the option `duplicates: Attach` links the existing object under the
  import's parent instead. Within one run two identical files are one blob and one object. A
  Markdown file is also deduplicated by its `id:` (M5 Decision 13 applies: a known live id is
  the same object and is updated, not duplicated). Rows of a CSV are not deduplicated against
  objects in M6; the report counts them per type.
- **Where imports land (Decision 4).** Under a parent the caller names, or under a new top-level
  object "Import <date>" typed `Import` (a new system type? no: a Note; Decision 4b) when none is
  named, so an import never scatters objects across the root. A folder import keeps its structure
  as children. The `Import` note's body lists the run (counts, duplicates, warnings) as the
  person's receipt.
- **The importers of v0.**
  - **Markdown and Obsidian folders:** the files folder's inbound engine, run once over the
    source folder with `StdFs`, with the guard off and a parent to land under, through a new
    `Mirror::import_from(vault, parent, options)`; every file's `id:` is adopted or re-issued by
    M5's rules, wikilinks resolve within the batch, frontmatter fields become fields of the types
    named, `#tags` become `Tag` relations, pictures the vault names are brought in as blobs and
    image blocks (the M5 deviation closes here: `![[attachments/x.png]]` and Obsidian's
    `![[pixel.png]]` both import when the file exists), and nothing is written back to the source
    folder (the mirror rows are not kept: the import is not a files folder). Provenance per
    object: `import:markdown`, `source_uri` the file.
  - **CSV and XLSX:** `csv` 1.4 and `calamine` 0.38. One type per file or sheet, named from the
    file or the sheet (an existing type of that name is reused and its fields matched by key), one
    field per column with its kind inferred from the column's values (number, boolean, date,
    datetime, URL, email, else text; a column that is all empty is text), the title from the
    first column unless an option names another, one object per row with the row's position as
    `sort_key`; a cell that does not fit the inferred kind is kept as text in the object's
    `props_json._import` and reported. BOM, delimiter (`,`, `;`, tab) and quoting are sniffed.
    Provenance `source_uri` is `path#sheet=<name>` for XLSX.
  - **PDF text:** `pdf-extract` 0.12 (over `lopdf`), text per page into paragraph blocks under a
    heading per page, the page count and the document's title and author (when the file names
    them) as fields of the `Document` type; the original attached. A file the crate refuses or
    that exceeds the caps is imported as a plain file with a warning, never dropped.
  - **Images:** `kamadak-exif` 0.6 for `DateTimeOriginal` → `captured_at`, GPS → `geo_lat` and
    `geo_lon`, camera make and model and orientation as fields of `Media`; `image` 0.25 for a
    256-pixel JPEG thumbnail attached with role `Thumbnail`, decoded under `image::Limits` (64
    megapixels, 256 MiB), orientation applied; the original attached; an image block in the body
    as the drop zone makes today.
  - **Any file:** the generic importer: sniff the MIME, attach the original to a `Document` (or
    `Media` for `image/*`, `audio/*`, `video/*`), no extraction. Archives are files in M6
    (Decision 5): nothing is unpacked, so a zip bomb is a blob of its compressed size and nothing
    more; unpacking is a later importer with its own caps.
- **Caps and safety (brief §10).** A source over 256 MiB is refused before it is read; a PDF is
  given at most 64 MiB and 10 s of extraction on the caller's thread (a budget the importer
  checks between pages, not a watchdog thread); image decoding runs under `Limits`; CSV cells are
  capped at 1 MiB and rows at 1,000,000 (the rest reported); a sheet or column name that is not a
  valid field key is slugged. Paths: a source path is canonicalised and must be a file or folder
  the person named; a folder import never follows symbolic links or junctions out of the folder
  (the `StdFs` rule) and names in archives are not an issue since none is unpacked. No importer
  reads anything but its source and writes anything but the vault. **No panics**: every importer
  returns `Err` for what it cannot read, and the fuzz tests assert it; `catch_unwind` is not
  used, since a panic in a dependency is a finding to fix or a crate to replace.
- **The shell and the UI.** Tauri's window drag-and-drop event (`DragDropEvent::Drop` with the
  paths) opens the Import dialog with those paths; the dialog also takes typed paths, as the
  files-folder override did in M5 (the picker is M7's onboarding work). The dialog shows the plan:
  one row per source (importer, what it becomes, counts, duplicates, warnings, a sample), the
  parent to land under, and Apply; after Apply, the receipt and "Undo" (the app's undo). An
  object's Document view shows its provenance under the title ("Imported from <file> on <date>
  by <importer>"), and the attachments it carries. Commands: `import_plan(sources, options)`,
  `import_apply(plan)`, `provenance_list(object_id)`; a `vault-changed` per transaction as usual.
  The e2e server has no native drop: the tests type paths under the session's data folder, as
  M5's used the folder on disk.
- **The CLI.** `dbme import <source> <vault>` gains `--into <id>`, `--dry-run` (prints the plan
  as JSON) and the formats above by sniffing; today's two forms (a full export, a Markdown folder
  into a **new** vault) stay.
- **Budgets (informational, not gated; the brief names none).** 10,000 CSV rows imported in under
  5 s in release on the reference machine; a 100-page text PDF in under 2 s; a 12-megapixel JPEG's
  thumbnail in under 500 ms. Printed by `budget.rs` in the ingest crate on Ubuntu, like M5's
  macOS leg.
- **Crates** (crates.io, 2026-11-03; each verified at gate 1 before use): `csv` 1.4.0
  (Unlicense OR MIT), `calamine` 0.38.0 (MIT), `pdf-extract` 0.12.1 (MIT) over `lopdf` 0.46.0
  (MIT), `kamadak-exif` 0.6.1 (BSD-2-Clause), `image` 0.25.10 (MIT OR Apache-2.0) with only the
  JPEG, PNG, GIF and WebP decoders and the JPEG encoder, `infer` 0.22.0 (MIT). All on the
  `deny.toml` allow-list. Gate 1a (below) verified pure Rust: no C in the tree; `pdf-extract`
  0.12.1 pins `lopdf` 0.42, not 0.46, and that `lopdf` carries `ttf-parser` 0.25, now under an
  unmaintained advisory (ignored with its reason in `deny.toml`); `calamine`'s `zip` 9 names
  `windows-sys`, a binding with no C that is absent from the Android and iOS trees. `pdf` 0.10
  (MIT) stays the fallback should `pdf-extract` fail a later fixture; gate 1c found no panic.
  `zip` is not taken by us (Decision 5); calamine reads its workbooks through it.

## Gate results (2026-11-03)

Every probe is an executable record in `crates/ingest/tests/`: `gate_tables.rs` (10 tests),
`gate_pdf.rs` (5), `gate_images.rs` (5) and `gate_provenance.rs` (4) assert what the crates do on
fixtures the tests build in memory (a stored zip of OOXML parts, PDFs from a handful of objects, a
PNG header, a JPEG that is only an APP1 segment), so nothing is copied from anywhere and a later
upgrade that changes a behaviour fails here first. Measured on the reference machine, debug build.

- **1a, the crates.** `cargo deny check`: licences, bans and sources clean with no new exception;
  one advisory, RUSTSEC-2026-0192, `ttf-parser` 0.25 unmaintained, reached only through `lopdf`
  0.42 inside `pdf-extract` 0.12.1 (which does not take `lopdf` 0.46); the crate forbids unsafe
  code and `lopdf`'s only caller of it is a font _writer_ that `pdf-extract` never calls, so the
  advisory is ignored with that reason and a review trigger. `cargo tree`: 111 crates under
  `dbme-ingest`, none with C; `windows-sys` and `windows-link` appear through `calamine` → `zip`
  9.3 and only on Windows (the Android and iOS trees have neither). `pdf-extract` takes `lopdf`
  without its `chrono`, `rayon` and `time` features.
- **1b, tables.** `calamine`: both sheets by name in order; inline strings; a cell styled with
  the built-in date format 14 is `Data::DateTime` with the serial kept (45992, 45993.5), and
  `is_datetime()` is true; numbers are `Float` even when whole; a formula cell gives its cached
  value in the range and its text (`C2*2`) in `worksheet_formula`; an all-empty column is `Empty`
  cells and a ragged row is padded with `Empty`; an unknown sheet and a zip without a workbook are
  errors (`FileNotFound("_rels/.rels")`). `csv`: the UTF-8 BOM is stripped from the first header;
  an embedded newline in a quoted cell is kept; a ragged row is `UnequalLengths` unless
  `flexible`; `;` and tab work when set, so the importer sniffs them; a 1 MiB cell reads whole;
  bytes that are not UTF-8 are a `Utf8` error as a `StringRecord` and readable as a `ByteRecord`.
- **1c, PDF.** `pdf-extract` on a two-page Helvetica PDF: the text, whole (3 ms) and by page
  (two strings, 3 ms). A scanned (image-only) page: `Ok("")`. Truncated at 90%, 50% and 20%:
  `Err("failed parsing cross reference table")` in under a millisecond each; plain text: `Err`
  on the header. A page tree whose root lists itself and a page whose parents loop: `Ok("")` in
  0.5 ms. A page tree declaring a million pages from 2.6 KB: five pages, 30 bytes of text, 10 ms
  (`lopdf` keys pages by object id, so repeated references collapse). No panic and no hang; the
  10 s cap stays as the importer's budget between pages (Design), not because a probe needed it.
- **1d, images.** An 8000×8000 grey PNG (64 megapixels, 316 KB encoded in 0.35 s) decodes under
  `Limits` (16,384 a side, 256 MiB) in 21 ms. A header claiming 100,000×100,000 is refused at the
  header read (`DimensionError`), before the dimensions come back; a reader without limits reads
  them, which is how the importer will say why. **Found:** 16,384×16,384 grey is exactly 256 MiB
  and passes `max_alloc`, so the importer's own pixel count (64 megapixels) is the guard that
  holds, with `Limits` beside it (Decision 14). A 640×480 JPEG round-trips and its 256-pixel
  thumbnail takes 21 ms and 7 KB. `kamadak-exif` reads orientation 6 and GPS 40°26'46.2" N,
  79°58'56" W from an APP1 segment with no image data; a JPEG without EXIF is `NotFound("JPEG")`;
  junk is an error. `infer` names JPEG, PNG, PDF and zip from their first bytes and nothing for
  CSV, so CSV and XLSX go by extension (and the workbook part for XLSX).
- **1e, the provenance op shape.** The drafted row (the brief's eleven columns) writes one stable
  JSON text and reads back equal; a payload with an extra column is refused. `confidence` writes
  as the number given and reads back bit for bit. **Found:** serde_json writes NaN and the
  infinities as `null` without an error, and `null` does not read back as a number, so such an
  op would never replay: the row's validation bounds `confidence` to 0..=1 (Decision 13). The
  chain hashes `provenance.create` and `provenance.delete` entries like any other kind (the kind
  is text), a changed confidence is a changed hash, and the previous hash is in it. Today
  `OpKind::parse("provenance.create")` is `UnknownOpKind` and `Entity::ALL` has eight entries,
  which Task 2 changes; the actions follow `attachment`'s pattern: create and delete only.

## Decisions to confirm

1. Provenance is an op-logged entity (`provenance` ops), not a side table, so it undoes, replays,
   exports and syncs with the objects it describes.
2. No `import_runs` table: the run is its ULID in `provenance.import_run_id` and its op groups.
3. Dedupe by content hash against `Original` attachments of live objects, and by `id:` for
   Markdown; CSV rows are not deduplicated in M6.
4. Imports land under a named parent or a new "Import <date>" note holding the receipt.
   - 4b. No `Import` system type; the receipt note is a Note.
5. Archives are plain files in M6; nothing is unpacked.
6. `dbme-ingest` is pure Rust with `dbme-mirror` behind a default feature; not in the mobile CI
   job until M14.
7. One transaction per run, split at 10,000 objects.
8. The files folder's inbound path writes no provenance row (the device is the provenance, M5
   Decision 1); the drop zone's extraction does, with `source_kind = import:<importer>`.
9. Typed paths and the desktop drop event in M6; the picker in M7.
10. No import budget is gated; the three informational figures are printed.
11. A cell that does not fit its inferred kind is kept as text under `props_json._import`, not
    dropped and not a failed row.
12. The crates named above, verified at gate 1; the `ttf-parser` advisory ignored with its reason.
13. `provenance` takes `create` and `delete` only, like `attachment`: a row is immutable and
    `accepted` is set when it is written; its `target_id` is the `object_id`, so an object's
    history and change events name the object; `confidence` is validated to 0..=1 (gate 1e).
    `source_uri` and `import_run_id` are optional (a `manual` or `clip` row has no run), and
    `original_blob` is not a foreign key to `blobs`: those rows exist only once an attachment
    refers to a blob and carries its size, which a provenance payload does not, so a replay could
    not create one; the service checks the blob store instead (Task 2).
14. The image guard is the importer's pixel count (64 megapixels) read from the header without
    limits, with `image::Limits` (16,384 a side, 256 MiB) beside it (gate 1d).
15. A table lands as a `Dataset` object holding the file (one per sheet under one per workbook),
    with the rows as its children, so the file is attached once and dedupe by hash works for
    tables too; the title column is the title and not a field; a kind wins a column when at most
    one cell in ten (and never fewer than one) does not fit it, a date column with a time in it
    is a datetime column, and the misfits are kept as text (Decision 11). An `Extract` names the
    types it needs (`TypeDraft`); the apply creates them or adds the fields an existing type
    lacks, whose kinds rule, inside the same transaction, so an undo takes the type too (Task 4).
16. A Markdown or Obsidian folder is imported by the files folder's engine in an import mode
    (`Mirror::import_from`, chosen 2026-11-03 over a second parser): the bookkeeping goes to
    scratch rows dropped at the end, so the vault's own files folder is untouched; every write
    is an ordinary `transact`, so the import is **one undo step per file** rather than one per
    run (the exception to Decision 7, and the engine's shape, not the plan's); what would have
    been an inbox entry is a warning on the receipt; a file whose `id:` the vault already has is
    taken as it is (the folder is the source, not a second editor to merge with), while a file
    without an `id:` is a new object each time it is imported; nothing is written back to the
    folder, so its files never gain ids or anchors. A file that is not Markdown becomes the
    engine's plain object and is then handed to the matching importer for what it can extract
    (`folders::enrich_object`: fields, the blocks it lacks, derived attachments, when and where);
    a table dropped into a folder stays a file, with a note to import it on its own.
17. The PDF parser's panics are contained, not trusted away (2026-11-03, found by the proptest
    layer in Task 9): `pdf-extract` 0.12 panics on some mutated files (a failed assertion on an
    operator's operands, unwraps on missing objects), which would have aborted a whole import
    for one bad file. The importer wraps the load and each page's extraction in
    `catch_unwind`; a panic costs that page (counted in a warning) or that file's text (a
    warning, confidence 0.5, the original still attached), never the run. The crate is pure
    Rust, so a panic is a bug and not memory corruption, and nothing of the document is kept
    after one. A panic that is a stack overflow or an abort is not caught by anything; none was
    found. The fuzz targets fuzz the importers' probes (`dbme_ingest::probe`, the CSV and PDF
    paths from the bytes on, no vault and no disk), so a panic they find is one past the
    containment. The hostile fixtures live in `fixtures/malicious-import/`, not in M5's
    `fixtures/malicious/`, because the files folder's test copies that folder whole and counts
    what it finds.
